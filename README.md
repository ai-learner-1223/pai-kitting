## 概要

すべて同じ白い立方体（4 cm）の部品 8 個が、2 列×4 個の整列トレイに置かれている。部品はくぼみの中で位置 ±5 mm・向き ±20° ずれている。
A・B・C の 3 種類があり、刻印ロゴ（A＝○、B＝＋、C＝△）だけで区別できる。ロゴは上面か底面にあり、どの面にもロゴがない不良品（刻印なし）も混ざる。

ロボットは次のように仕分ける。

- 手先カメラでトレイを撮影し、認識CNNで各部品の位置・向き・上面のロゴを判定する。部品を 1 個仕分けるたびに撮り直す。
- 上面にロゴがある部品は、**模倣学習した方策**で種類のトレイへ運ぶ。
- 上面にロゴがない部品は、つかんで検査位置へ運び、**下から見上げる検査カメラ**で底面を確認する（能動的な認識）。
  - 底面にロゴがあれば、その種類のトレイへ置く。
  - 底面にもなければ、**不良（刻印なし）**として「?」のトレイへ置く。
- つかみ損ねは指の開きで検知し、撮り直してつかみ直す。

すべて物理シミュレータ MuJoCo 上で動作し、GPU は不要（CPU のみ）。

## 処理の流れ

```
          ┌──────────────── 部品を 1 個仕分けるたびに繰り返す ────────────────┐
          ▼                                                                    │
  撮影姿勢へ → 手先カメラで撮影 → 認識CNN（画素ごとに 背景／上面／側面／○／＋／△）     │
          │                         → 部品ごとの 位置・向き・上面の種類            │
          ▼                                                                    │
   次の部品（トレイの端から順）                                                    │
          │                                                                    │
     ┌────┴──────── 上面にロゴあり ─────────┬──────── 上面にロゴなし ─────────┐   │
     ▼                                    │                                 ▼   │
  模倣学習した方策で種類のトレイへ             │        つかんで検査位置へ（IK）        │
 （関節角・把持状態・部品位置・置き場所        │        → 検査カメラ → 識別CNN        │
   → 1 秒先までの関節目標）                  │      ロゴあり：種類のトレイへ（IK）    │
     │                                    │      ロゴなし：不良として「?」へ（IK）  │
     └────────────────────────────────────┴──────────────┬──────────────────┘   │
                                                           └───────────────────────┘
       ※ 撮影のあと「前の部品を置いた直後の姿勢」へ戻してから方策へ渡す（方策の学習時の開始状態）
```

## ベースライン（最終課題サンプル）との関係

ベースラインは最終課題サンプル「Pick and Place Task - ROS2 Gazebo Simulation (UR3 + Robotiq 2f-85)」（IFRA Cranfield, 2023）。

| | サンプル | 本システム |
|---|---|---|
| タスク | 立方体 1 個の pick & place | 8 部品を整列トレイから連続で種類別に仕分け |
| 動作の生成 | 固定スクリプト（MoveJ → MoveL → Attach → …） | 模倣学習した方策（推論のみ）。スクリプトはデモの生成と検査動作に使用 |
| 把持 | 物体を手先にリンクで固定するプラグイン | 指の接触と摩擦による物理的な把持 |
| 認識 | なし（物体位置は既知） | 手先カメラの画像から CNN で位置・向き・種類を推定 |
| 検査 | なし | 上面にロゴがない部品だけ持ち上げ、検査カメラで底面を確認。底面にもなければ不良と判定 |
| AI | なし | 認識CNN（手先カメラ用・検査カメラ用）、模倣学習方策 |
| 環境 | ROS 2 Humble ＋ Gazebo | MuJoCo（Python のみ、CPU で動作） |

講義との対応：第5回の「デモ収集 → 学習（ACT）→ デプロイ → 方策のデバッグ（正解と予測の比較）」の流れを、
テレオペの代わりに、IK で関節角を計算して決まった手順で動かすプログラム（スクリプト方策）でデモを集める形で、シミュレーション上に再現した。アクションチャンキングと
時間方向の加重平均（temporal ensembling）は ACT と同じ考え方。

## 主な結果

### 能動的な認識の効果（20 シーン・160 部品。底面ロゴの良品 58 個、どの面にもロゴがない不良品 10 個）

どの方式も、部品を 1 個仕分けるたびに手先カメラで撮り直す。

| 方式 | 種類・不良の識別 | 不良の検出 | 仕分け成功 | 検査回数 | 1 シーンの時間 |
|---|---|---|---|---|---|
| (A) 上面だけ見る（読めなければ「?」へ） | 92/160 | 0/10 | 102/160 | 0 | 74.9 秒 |
| (B) 全部品を検査する | 160/160 | 10/10 | 159/160 | 161 | 123.6 秒 |
| (C) 必要なときだけ検査する（提案手法） | **160/160** | **10/10** | **159/160** | **68** | **94.0 秒** |

- (C) は (B) と同じく全部品の種類と不良を判定し、検査回数を 58%、時間を 24% 減らした。
- (A) では底面ロゴの良品も不良品も「?」へ行き、区別できない（(A) の仕分け成功のうち 10 個は、不良品がたまたま「?」へ行ったもの）。
- 上から読めない部品は、トレイの容量の都合で 1 シーン 4 個以下にしている。観察の順序（上面 → 底面 → なければ不良）は固定のルール。
- (C) の失敗 1 件は、上面にロゴのない部品の位置推定が約 1 cm ずれて端をつかみ、運ぶ途中で落ちたもの。

### 基本の設定（底面ロゴ 15%、読めない部品は「?」のトレイへ、最初に 1 回だけ撮影）

| 項目 | 結果 |
|---|---|
| 認識（手先カメラ、40 シーン・320 部品） | 種類の正解 319/320（見落とし 1）、位置誤差 平均 0.3 mm、向き誤差 平均 0.3° |
| 方策：改善前（単発デモで学習） | 毎回ホームから：160/160（100%） ／ 連続作業：24/160（15%） |
| 方策：改善後（連続動作のデモで学習） | 連続作業：160/160（100%） |
| スクリプト方策（IK） | 連続作業：160/160（100%） |
| 統合実行（手先カメラ → CNN → 方策、20 シーン） | 仕分け成功 158/160、全数成功 18/20 シーン |

### 汎化性能の検証（再学習なし、各条件 8 部品 × 10 シーン）

| 条件 | スクリプト方策 | 学習方策 |
|---|---|---|
| 学習時と同じ（±5 mm・±20°） | 80/80 | 80/80 |
| 位置ずれ ±10 mm ／ ±15 mm | 80/80 ／ 80/80 | 80/80 ／ 80/80 |
| 向きずれ ±30° ／ ±45° | 80/80 ／ 79/80 | 80/80 ／ 67/80 |
| 供給トレイを 3 cm 手前 ／ 奥へ | 80/80 ／ 80/80 | 67/80 ／ 79/80 |
| 部品位置に誤差 2・4・6・8 mm | すべて 80/80 | すべて 80/80 |

学習方策は、大きな位置ずれや認識誤差には強いが、入力が学習範囲の外に出る条件（向き ±45°、手前へ移したトレイ）で成功率が下がる。

### LeRobot の ACT との比較（同じデモ・同じ評価、`lerobot/`）

| 評価 | 自作の方策（MLP、約 58 万パラメータ） | LeRobot の ACT（約 580 万パラメータ） |
|---|---|---|
| 方策のみ（部品の位置は真値、20 シーン） | 160/160、49.8 秒 | 152/160、66.0 秒 |
| 能動的な認識の全体（方式 (C)、20 シーン） | 仕分け 159/160、94.0 秒 | 仕分け 156/160、103.9 秒 |

入力が 14 次元の数値だけの問題では、軽い MLP のほうが成功率も速さも上だった。

### 再現性

別の PC（WSL2 Ubuntu 24.04、Python 3.12、venv、CPU 8 スレッド）で `reproduce.sh quick` を実行し、上記の結果（12 項目）が
1 項目を除いて完全に一致することを確認した（所要 67 分）。違いは (B) の検査回数のみ（161 → 160。つかみ損ねたあとのやり直しの有無）で、識別・仕分けの結果は同じ。

## 実行方法

想定環境：Windows の WSL2（Ubuntu 24.04）。GPU は不要（すべて CPU）。メモリは 8 GB 以上を推奨。

### 1. ファイルを置く

```bash
cd ~
git clone <このリポジトリの URL> pai_kitting     # または zip を展開する
cd pai_kitting
```

### 2. 環境を作る（初回のみ、10 分程度）

Ubuntu 標準の Python と venv を使う場合：

```bash
bash setup_venv.sh                 # OSMesa（画面なし描画）・日本語フォント・Python パッケージ（CPU 版 PyTorch）
unset PYTHONPATH                   # ROS 2 を入れている環境では、ROS の Python パスを外す
source ~/pai-venv/bin/activate
cd sim
python check_env.py                # すべて [OK] なら準備完了
```

Miniforge（conda）を使う場合は、`bash setup_env.sh` → `conda activate pai` → `cd sim` → `python check_env.py`。

ターミナルを開き直したときは、毎回 `unset PYTHONPATH` → `source ~/pai-venv/bin/activate` を実行してから作業する。

### （別の方法）Docker で動かす

venv の代わりに、環境ごとコンテナにして動かすこともできる。ROS 2 など他の Python 環境と混ざらない。

Docker の準備（初回のみ。Docker Desktop の WSL 連携を使ってもよい）：

```bash
sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2
sudo usermod -aG docker $USER      # sudo なしで docker を使えるようにする。いったん WSL を閉じて開き直す
```

イメージを作って実行する（リポジトリの最上位フォルダーで）：

```bash
mkdir -p sim/out sim/logs                              # 結果の書き出し先（先に自分で作っておく）
docker compose build                                   # イメージを作る（初回 10 分程度）
docker compose run --rm sim                            # 環境の確認（check_env.py）
docker compose run --rm sim bash reproduce.sh quick    # 再現（約 1 時間）。結果はホストの sim/out に出る
docker compose run --rm sim python active.py eval active 20   # 個別のコマンドも同じ形で実行できる
```

`sim/out` を作らずに実行すると、Docker が root 所有で作ってしまい、書き込めずに失敗する。そのときは `sudo chown -R $USER sim/out sim/logs` で直す。

### 3. 再現する

```bash
bash reproduce.sh quick 2>&1 | tee quick.log     # 学習済みモデルで 評価 → 3方式の比較 → 録画 → 図（約 1 時間）
```

| コマンド | 内容 |
|---|---|
| `bash reproduce.sh quick` | 同梱の学習済みモデルで、評価・3 方式の比較・動画・図を作る（学習なし） |
| `bash reproduce.sh full` | データ生成・デモ収集・学習から全部やり直す（元のモデルは `kit_data/bundled/` に退避） |
| `SMALL=1 bash reproduce.sh full` | 規模を小さくして手順だけ確認（数値は参考にならない） |
| `WITH_BASIC=1 bash reproduce.sh quick` | 基本の設定の動画（`out/final_video_task.mp4`）も作る |
| `bash kit_robust_all.sh` | 汎化性能の検証（各条件 10 シーン、結果は `out/robust_*.json`） |

最後に、提出時の結果（`out_reference/`）と再現結果の比較表が表示される（`python compare_results.py` でも表示できる）。
quick は同梱モデルを使うため、数値はほぼ一致する。full は CPU の違いで学習結果がわずかに変わることがある。

実行中は PC をスリープさせないこと（WSL が止まり、処理も止まる）。

## 開発中に見つけた問題と対策

1. **単発デモだけでは連続作業に汎化しない（分布シフト）**
   部品ごとに腕をホーム姿勢へ戻して記録したデモで学習した方策は、毎回ホームから始めれば全数成功するが、
   前の部品を置いた姿勢からそのまま次へ向かうと、2 個目以降でほぼ失敗する。本番と同じ連続動作のデモで学習すると解決した。
2. **検査や撮り直しのあと、方策にどの状態で引き継ぐか**
   検査（IK）のあと「学習時と同じホーム姿勢」に戻してから方策に渡すと、仕分けに失敗した。この方策にとっての
   学習時の開始状態は「前の部品を置いた直後の姿勢」だった。撮り直しのあとも、この姿勢へ戻してから渡すようにした。
3. **まれな状況はデモに出てこない**
   基本の設定での失敗 2 件のうち 1 件は「判別不能」トレイの 4 つ目の置き場所で、学習デモ 2,000 本中に 5 回しか現れない状況だった。
   もう 1 件は、ロゴのない上面がアーム自身の影に入り、部品として検出されなかった見落とし。
4. **つかみ損ねと運搬中の落下**
   つかみ損ねたまま検査すると、空の手を「底面にもロゴなし＝不良」と誤判定した。指の開きで把持を確認し、撮り直してつかみ直すようにした。
   また、部品を持って大きく動く途中の落下を減らすため、運搬を遅くし、上方の中継点を通るようにした。
5. **手先カメラでの位置のずれ**
   斜め上から撮るので部品の側面も写り、側面を含めて重心を取ると 2〜8 mm ずれた。上面と側面を CNN で見分け、
   カメラの姿勢（関節角から計算）を使って上面の高さの平面へ投影して解消した。
6. **7 自由度アームの冗長性**
   同じ手先位置でも IK の初期値で関節姿勢が変わる。IK を常に基準姿勢から解き、方策の入力分布を一定にした。

## 限界と今後

- シミュレーションのみ。実機ではカメラのノイズ、照明、把持の滑りなどの差がある。
- デモは人のテレオペではなく スクリプト方策で生成しているため、デモ自体のばらつきが小さい。人のデモのばらつきへの対応は未検証。
- 検査の動作は IK で、方策には学習させていない。観察順序も固定のルール。
- 方式 (C) が検査を省けるのは「上面のロゴが読めれば底面を見る必要はない」という部品の仕様が前提。底面に独立した欠陥がありうる工程では、全数検査などとの併用が必要。
- 今後の課題：
  1. 検査の動作も含めたデモで方策を学習する
  2. 観察のコストと不確かさから、次に見る面や検査の要否を選ぶ（POMDP など）
  3. ROS 2 ＋ 実機への移植、Transformer（ACT）や拡散方策との比較
  4. ロゴを側面にも置く 6 面検査への拡張（指で挟んでいる面は隠れるため、つかみ直しの計画と視点の選択が必要）
